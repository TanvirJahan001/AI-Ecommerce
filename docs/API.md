# Application and Integration Contracts

**Purpose:** proposed store API contract; provider endpoints are deliberately unspecified until official merchant documentation/access is verified. **Status:** proposal. **Updated:** 2026-11-14. **Related:** [DATA](DATA.md) · [USERS](USERS.md) · [SECURITY](SECURITY.md) · [Architecture](Architecture.md).

All JSON uses UTF-8; money `{currency:"BDT", amount_minor:125000}`. Errors `{code,message,field_errors?,request_id}`. Server recalculates catalog price, promotion, delivery quote and total. Every mutation validates input and actor/object ownership; admin role checks server-side. State names follow [DATA](DATA.md).

Representative fictional response:

```json
{
  "order_id": "ord_ex_1042",
  "status": "pending_payment",
  "currency": "BDT",
  "total_minor": 145000,
  "payment": {
    "attempt_id": "pay_ex_1",
    "status": "pending",
    "redirect_url": "provider-returned-url"
  }
}
```

Provider adapter boundary: only provider-returned handoff/verification fields accepted; do not invent provider URLs or payloads. Redirect is not verification. Verify transaction reference, amount, currency, merchant/order association, final status and authenticity using selected provider’s current official docs and account credentials. Repeated events dedupe; delayed/out-of-order events reconcile against authoritative transaction status; a success after cancel/expiry becomes reconciliation_required. Never fulfill twice. If pending/ambiguous, keep order exception and retry verification; failed permits safe retry with fresh attempt/idempotency. Customer screenshots are support evidence only. Refund API may submit provider refund if supported and approved; COD refund records bank/mobile/manual payout reference and verified completion, without assuming automatic reversal. Rate limits, CSRF/session and webhook controls in [SECURITY](SECURITY.md).

## Implementation command contracts (R2–R6)

All commands accept `Idempotency-Key`; persist key, actor, request hash and result. Reuse with different payload returns `409 IDEMPOTENCY_KEY_REUSED`. Every mutation writes audit/outbox records in the same transaction as state change. Roles are canonical: `store_owner`, `catalog_manager`, `fulfillment_operator`, `support_agent`, `finance_operator`; customers act on own authenticated orders, guests require valid order proof. See [USERS](USERS.md), [SECURITY](SECURITY.md). Initial deployed configuration provisions only `store_owner`; other roles fail closed until explicitly implemented.

| Command                                         | Actor / inputs                                                                  | Preconditions; transaction effects                                                                                                                             | Retry and errors                                                                     |
| ----------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `POST /api/admin/orders/{id}/cod-confirm`       | `store_owner` or `support_agent`; confirmation source/reference                 | order `awaiting_cod_confirmation`, COD enabled/eligible; commit existing reservation atomically; record event                                                  | unique idempotency; 409 wrong state, 422 COD disabled/unavailable                    |
| `POST /api/admin/shipments/{id}/cod-collection` | `fulfillment_operator` or owner; amount, time, evidence/reference               | dispatched COD shipment; amount ≤ COD due and not already collected; create immutable verified-cash collection/funding                                         | unique collection key; duplicate returns original, amount conflict 409               |
| `POST /api/admin/orders/{id}/cancellation`      | customer/guest proof may request; owner/support approves or rejects with reason | pre-dispatch only; approve releases commitment once, cancels pending attempts and opens refund only for verified funding; reject leaves stock/status unchanged | command key; 409 dispatched/paid conflict, 422 policy ineligible                     |
| `POST /api/admin/orders/{id}/returns`           | customer/guest proof requests; owner/support authorizes/rejects                 | order item and quantity eligible; authorize creates expected return, reject records reason; no stock/refund effect yet                                         | key unique; duplicate stable result; 409 ineligible                                  |
| `POST /api/admin/returns/{id}/receipt`          | `fulfillment_operator` or owner; item quantities, package condition/evidence    | authorized and in-transit; received qty ≤ authorized remaining; increment physical and quarantine, create inspection lot                                       | unique receipt event; 409 excess/duplicate mismatch                                  |
| `POST /api/admin/returns/{id}/inspection`       | `fulfillment_operator` or owner; per-item condition and reason                  | received and not already inspected; record disposition; stock remains quarantine until follow-up action                                                        | idempotent inspection key; 409 not received/already conflicting                      |
| `POST /api/admin/returns/{id}/disposition`      | owner or `fulfillment_operator`; qty and `restock`/`damaged_writeoff`           | inspected, qty within inspected unassigned; restock releases quarantine; writeoff remains unavailable and records physical adjustment                          | unique disposition key; 409 qty/state conflict                                       |
| `POST /api/admin/refunds/{id}/approve`          | `store_owner` or `finance_operator`; amount/item allocations/funding ID         | verifies funding, received item quantity, deterministic allocations; locks funding ledger; reserves refundable capacity and item quantities                    | idempotent; 409 capacity/qty exhausted, 422 bad allocation                           |
| `POST /api/admin/refunds/{id}/submit`           | `store_owner` or `finance_operator`; payout channel                             | approved commitment exists; atomically marks submitting and creates payout attempt/outbox before network call                                                  | same idempotency/provider key on retry; timeout → `unknown`, capacity stays reserved |
| `POST /api/admin/refunds/{id}/reconcile`        | `store_owner` or `finance_operator`; provider/manual evidence and outcome       | pending/unknown/failed attempt; verified success converts reserved amount to succeeded; definitive failure releases reservation; ambiguous preserves it        | unique evidence event; 409 contradictory result routes to reconciliation             |
| `POST /api/admin/warranty-claims/{id}/resolve`  | `store_owner` or `support_agent`; outcome/reason/evidence                       | claim received and open; records accepted/rejected/repair/replacement/refund referral per owner policy; no implied stock/refund without separate commands      | unique decision key; 409 already resolved; re-open only audited owner command        |

Errors include `401`, `403`, `404` (including concealed cross-owner object), `409` state/idempotency/capacity conflict, `422` validation/policy, `429` rate limit, and `503` retryable dependency. Out-of-order notifications are recorded before processing; state machine preconditions prevent regression. Webhook acknowledgement means durably accepted, not necessarily commerce-completed; unresolved events enqueue reconciliation.

### Guest order-access contract

Anonymous cart session uses random 256-bit cookie `HttpOnly; Secure; SameSite=Lax`, scoped path, with only a hash/reference stored server-side and expiration. At order creation issue separate random 256-bit order-access secret; persist only SHA-256/HMAC hash, order ID, scope (`read_tracking`, `request_cancel_return`), created/expiry/revoked timestamps, and issuance idempotency key. Return the secret once on order confirmation over TLS and set an HttpOnly scoped cookie for the current device; never include in analytics/logs. A signed link may be sent only through a configured delivery channel; development uses an explicit local mail sink showing recipient and link. After browser closure, same-device cookie or saved secure link restores limited access. Expired/lost credential recovery requires OTP to a separately verified phone channel and order reference/rate limits; delivery phone alone is not proof, and until a real OTP provider is configured, recovery is owner-assisted after independent ownership evidence. Support staff cannot disclose tracking/order details solely from a phone number. Revoke token on verified recovery, suspected exposure or owner action. Rate-limit by IP/session/phone/order and return generic errors. No anonymous order writes other than allowed cancellation/return requests; no address/payment changes.

## Implemented HTTP transport — 2026-11-14

The initial app consolidates the proposed operations behind `GET /api/store?resource=...` and `POST /api/store {action,...}`. Earlier REST paths remain logical proposals, not duplicate live endpoints. GET resources: catalog, cart, owned orders, account history, public content, owner admin queues and reports. POST actions: cart.add/remove, quote, discount.apply, checkout, payment.retry/simulate, request, recovery.start/complete, account.link, admin.command. Exact validation and wire fields live in [route](../src/app/api/store/route.ts); domain preconditions remain in DATA and the command tables above. Cookie mutations require matching APP_ORIGIN. Errors have code/message and HTTP status. Owner export is `/api/admin/export`; auth uses `/api/auth/*`.

The implemented guest credential is a random 256-bit shopping cookie (`shop`, HttpOnly, SameSite=Lax, Secure in production), issued by the API and hashed before persistence. Checkout atomically grants that session access to its order. Only public status/items, cancellation/return/warranty requests and verified account linking are allowed. Grants and cookies last 30 days and support reopening the browser. Expired/lost-device recovery matches the order contact email then requires an expiring code delivered by the isolated development sink; matching contact alone does not grant access. Three starts/order/hour, five code attempts, ten-minute challenge expiry, and one-time use apply. Recovery revokes old grants. Real-channel recovery is disabled until an approved adapter exists; support may investigate but cannot bypass proof merely from a phone number.

Checkout takes client-reviewed expected_total_minor and recomputes amounts server-side. HTTP idempotency binds the original request and session before repricing/cleared cart checks. Only development explicitly enables simulated payment events. Real provider endpoints/webhook authentication remain unimplemented pending official account documentation and sandbox proof. Owner manual courier commands are implemented. COD refunds use recorded customer collection and separate payout evidence, never the development gateway as an automatic COD reversal.

Owner commands also include store.configure (method flags and district rate), notification.template (plain text title/body keyed by topic), support.note (bounded order-scoped note), and variant.details (structured source/spec/fit/media). All are owner-MFA/origin gated and audited. Delivery eligibility uses configured district rates; unsupported destinations fail. No production method is enabled merely by changing local flags.
